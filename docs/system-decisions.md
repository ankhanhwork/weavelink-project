# WeaveLink implementation decisions

Version 1.0 — 2026-09-19. These are new implementation decisions made under the project owner's approved specification-reconciliation plan. They are not claims about DBIZ2 author intent, a lecturer's approval, or a production legal agreement. All 12 MFG modules are in the complete-system target; old Session 1 MVP exclusions are historical only. Existing MFG, F, UC and S identifiers remain stable. Read this document before module and screen specifications; if a conflict is found, repair the dependent document to this contract.

## D01 — Actors, tenancy and access

Guest is anonymous; Member means an authenticated active user, not a separately assignable role. Assignable roles are Customer, Sales Consultant, Company Admin and System Admin. Public registration creates Customer only. A customer can use multiple companies; each product, design request, order, contract, payment, consultation and batch belongs to exactly one company. Customer access also requires ownership. Staff access requires matching company_id; consultants additionally require assignment. System Admin manages company accounts/configuration/logs/backups, but has no implicit access to customer designs, order mutations or company financial exports. Enforce all rules on the server, not just hidden UI. Return 401 for missing authentication, 403 for prohibited operations and 404 for inaccessible object identifiers.

CompanyAccount consists of a Company and its staff memberships, not a customer's identity. Only System Admin provisions Company Admin/Sales Consultant memberships and companies. Protect the last active System Admin and last active Company Admin in an active company from deletion/demotion. Deletion is soft deletion plus session revocation; retain historical business records. Suspending a company blocks new catalog/order/payment activity but preserves customer read access and payment reconciliation; System Admin must resolve open work through reactivation before deletion.

## D02 — Common data and interfaces

Company lifecycle is Provisioning -> Active -> Suspended -> Active, with Provisioning/Active/Suspended -> Deleted only after open-work checks. Company creation atomically creates its pending initial-admin invitation; it becomes Active only when the invitation is accepted. Existing identities authenticate before acceptance; new invited staff set their name/password using S03 invitation mode and verify email by consuming the invite. Acceptance atomically links/creates identity, activates membership and consumes the invite. Customer is a user capability; staff roles are per-company Membership records, while System Admin is a system capability. A single global user.role must not replace company membership checks. Staff select an active company from authorized memberships; customers derive company scope from their resource/product, not from a freely trusted request field.

Identifiers are scoped: MFG-07 and MFG-08 both inherited F-ORD-001 through F-ORD-007. Preserve the source IDs but always reference them as MFG-07/F-ORD-003 or MFG-08/F-ORD-003 outside their own module. FR and US IDs are also module-local. The canonical requirement identity is (module_id, function_id), not function_id alone. UC IDs remain globally unique, including aggregate use cases that map to child functions rather than new duplicate functions.

Use UUID identifiers, ISO-8601 UTC timestamps, display timezone Asia/Ho_Chi_Minh, integer VND amounts and integer quantities. Store immutable created_at and mutable updated_at/version. Money fields never use floating point. User identity/company/permissions come from the server session; never trust a submitted customer_id, price, signature IP or role. Optional text is null or trimmed text, not an invented value.

List requests use page >= 1 (default 1), page_size 1..100 (default 20), allowlisted sort/filter fields; responses use items,total,page,page_size. Errors use code,message,field_errors,request_id, with 400 malformed request, 422 invalid fields, 409 stale version/state/duplicate conflict, 429 rate limit and 503 temporary dependency failure. Mutations include expected_version; financially significant create/sign/pay/batch requests additionally use an Idempotency-Key UUID. Same key and same payload returns original result; changed payload is 409. Keep keys at least 7 days and permanent uniqueness for provider transaction/event IDs. Use transactions, unique constraints and an outbox for side effects.

Screen functions return a view model rendered by the client, not a database UI type. Form navigation takes route parameters and current session; forms without business input take no request body. Files are private stored assets referenced by UUID; downloads require access checks and expiring URLs (10 minutes). Upload images: PNG/JPEG/WebP, at most 10 MiB each and 5 files/request; check actual MIME, scan and reject unsafe content. Contract PDFs are generated server-side. Strings render as text; never execute uploaded HTML or template code.

## D03 — Authentication and notifications

Version checks apply to existing objects being edited; a new entity has no client-supplied version unless it references a parent/quote whose version must be checked. Browser mutations require CSRF; signed provider callbacks and trusted scheduled jobs use their own authenticated authority and server-side locks, never a browser session or client expected_version. Registration, invitations and password links are not ordinary authenticated CRUD.

Use email/password, email verification links (24 hours), password-reset links (30 minutes), and staff invitation links (48 hours). Tokens are cryptographically random, stored hashed, single use; resend invalidates prior token. Email is case-normalized, globally unique; full_name 1..100 characters; password 12..128 characters with spaces supported. Store a password hash, never reversible encryption. Generic reset/resend responses do not reveal account existence. Allow at most 5 failed attempts per account/IP in 15 minutes (the fifth returns generic 401; subsequent attempts return 429 until the window clears) and link requests to 3 per account/IP/hour. Password change requires current password and revokes other sessions; reset revokes all sessions. Use revocable server sessions via Secure, HttpOnly, SameSite=Lax cookies, CSRF protection on mutations, 30-minute idle and 24-hour absolute expiry. Post-login return paths must be internal allowlisted routes.

Persist notifications in an outbox in the same transaction as the business event. In-app inbox is authoritative; SMTP email is secondary. Retry email after 1, 5 and 30 minutes, then mark delivery failed for operations retry. Email failure never rolls back signing, payment or assignment. Event/recipient uniqueness prevents duplicate notices. Development uses a local email sink and VNPay sandbox; actual SMTP/provider secrets are environment settings, never committed or requested in the user-input file.

## D04 — Products and designs

Capacity means max_units_per_order (integer 1..10000), not warehouse stock or a reservation pool. The total size quantity must not exceed this limit at quote and submission; return 422 CAPACITY_EXCEEDED otherwise. Capacity changes invalidate unconsumed quotes but never edit submitted orders. Business operators use batching/production queues to schedule accepted work. Product SKU lookup always uses company_id plus SKU; public canonical URLs use globally unique product UUIDs.

Product states: Draft -> Published -> Hidden; Draft/Hidden/Published -> Archived (terminal). Published requires name, company-unique SKU, nonnegative unit_price_vnd, category, at least one safe image, supported sizes/colors/materials and manufacturing capacity. Archive removes public visibility but preserves references. No checkout for Hidden/Archived products. Made-to-order capacity is validated at quote/submit, not treated as a reserved stock count. S12 edits product content; S14 edits product design rules for the same product (corrects the duplicate legacy title).

Design is a versioned configuration tied to product_id, product_version, customer_id and company_id. Use a 2D preview with print-area coordinates; 3D is not required. Saved self-designs and delivered consultant designs are orderable; drafts are not. Validate options against product rules, image bounds and asset access. A changed product/rule invalidates an old quote and requires explicit review; existing submitted orders keep immutable snapshots. Consultant delivery creates a new immutable design version and notifies its owner; editing an ordered design creates a copy/version, never changes an order snapshot.

## D05 — Design service and consultations

Create DesignRequest before payment, status AwaitingPayment. Fields: id,company_id,customer_id,product_id,requirements (20..5000 chars),attachment_ids,requested_deadline,fee_vnd,status,version. Deadline must be at least 3 calendar days in the future at submission. Fee defaults to 200000 VND, snapshotted at creation; this is a configurable classroom assumption. One successful SERVICE payment changes AwaitingPayment -> Paid and creates the actionable admin notification; no assignment before Paid. Unpaid requests expire after 24 hours or can be cancelled. Paid -> Assigned -> InProgress -> Delivered; Company Admin assigns an active same-company consultant, consultant delivers a valid design. The requested deadline is a request, not a guaranteed promise; admin records committed_due_at at assignment and customer sees it. Paid/unassigned requests may be cancelled with a full refund; after assignment cancellation is rejected. Payment settlement/refunds use D08.

CRM Consultation is separate: New -> Contacted -> InProgress; InProgress -> ClosedWon or ClosedLost; New/Contacted may close early as ClosedLost. Store customer_id,company_id,consultant_id,notes and related request/order IDs. Reopening a closed consultation to InProgress requires Company Admin. Assignment is scoped to a specific company/customer; design request assignment must use that customer's assigned consultant or atomically reassign both. Only assigned consultant/company admin can read notes; customer sees own request status/delivery, never internal notes. Consultation outcomes do not change order status.

## D06 — Quote, amounts and submission

Price-policy v1 fixes merge discount 5%, standard production 7 days and merge allowance 3 days. These are read-only policy constants in configuration; changing them requires a new reviewed policy version and corresponding specs. Design-service fee and shipping charge remain configurable and are snapshotted. Quantity or preference changes create a replacement immutable quote and invalidate the old quote; never mutate quote amounts in place. Submitting one quote twice, even with different idempotency keys, returns the same order via a unique consumed_quote_id constraint. Subtotals and totals use checked integer arithmetic; payment totals must be positive and <=9999999999 VND.

One order contains one product/design version with quantity_by_size (each positive integer, total 1..10000), one company and one shipping address. Multi-company carts and mixed-design orders are outside this version. Address requires recipient_name 1..100, phone 8..15 digits with optional leading +, address_line 1..250, ward 1..100, province 1..100, country VN. Product default unit_price applies equally across sizes; option surcharges are nonnegative VND per unit stored in product rules.

Server quote: subtotal_vnd = sum(size_quantity * (unit_price_vnd + option_surcharge_vnd)); merge_discount_vnd = floor(subtotal_vnd * 5 / 100) if eligible opt-in else 0; shipping_vnd = 30000; merge_fee_vnd = 0; tax_vnd = 0; total_vnd = subtotal_vnd - merge_discount_vnd + shipping_vnd + merge_fee_vnd + tax_vnd. Tax zero means classroom demo pricing, not a statement of Vietnamese tax law. No promo codes in this release; omit nonfunctional promo/generate-code controls from the implementation. Display the full breakdown in S23/S25/S34/S35; dollar values in old PNGs are illustrative only. A quote lasts 30 minutes and has an immutable quote_id, product/design versions and policy_version. Requote expired/changed inputs and require review before submission.

Submitting a valid quote creates Order(PendingContract), items/address/price snapshots and merge preference atomically. Customer cannot submit a different total. No batch is created at checkout. Order contains id,company_id,customer_id,design_id,design_version,quote_id,status,merge_opt_in,policy_version,contract_id nullable,batch_id nullable,shipping_address,quantity_by_size,price_snapshot,version,created_at. Monetary/configuration changes apply only to new quotes.

## D07 — Order and contract lifecycle

Order transitions: PendingContract -> AwaitingPayment (only after signing the current contract); AwaitingPayment -> Confirmed (verified full payment); Confirmed -> InProduction -> Shipped -> Delivered. PendingContract/AwaitingPayment/Confirmed -> Cancelled is allowed only when no batch_id and production has not started. Confirmed cancellation schedules a full refund; a cancelled order stays Cancelled while refund state is tracked separately. Customer can cancel own eligible order; company admin can cancel with a reason; consultants cannot cancel or bypass payment gates. Consultant assigned to that customer or Company Admin updates fulfillment; shipment requires carrier,tracking_number and shipped_at. Delivery records delivered_at. Repeated transition to current state is a no-op; skipping/reversing states is 409. Payment failure leaves order AwaitingPayment. Customer must cancel before production to change submitted contents/address; make a new order, never edit a signed snapshot.

Company Admin generates a contract using a versioned template and order snapshot. Contract states Draft -> Ready -> Signed; Draft/Ready -> Superseded; Draft/Ready/Signed -> Voided on eligible order cancellation. Publish Ready only after PDF generation/storage succeeds. Admin can replace an unsigned contract version and notify customer; cannot edit Signed. Contract carries id,order_id,version,template_version,content_hash,pdf_asset_id,status,ready_at,signed_at,signature_evidence. Signing uses authenticated customer, explicit consent, typed full name and password reauthentication within 5 minutes, with a server-generated one-time signing challenge bound to contract ID/version/hash (10-minute lifetime). Evidence stores signer_id,typed_name,consent_text_version,contract_hash,server_timestamp,server-observed IP,user_agent and challenge digest. This is an application acknowledgement with an audit trail; it does not claim a qualified/certified digital signature. Checkbox alone is insufficient. S34 submits the challenge and evidence inputs; repeat same signing key returns the signed version. Transaction locks contract/order and rejects stale/superseded versions; only successful signing changes order to AwaitingPayment. Send copies through the outbox after commit. PDF access remains authorization-checked.

## D08 — Payment and refund

Shared PaymentTransaction belongs to exactly one purpose ORDER or SERVICE and its order_id or request_id (exclusive). Fields: id,purpose,resource_id,company_id,customer_id,amount_vnd,currency=VND,status,provider_reference,provider_transaction_id nullable,created_at,expires_at,paid_at nullable,refund_status,version. Payment attempt states Pending -> Succeeded / Failed / Expired. Refund states None -> Pending -> Succeeded / Failed. One active Pending attempt per resource, reused for repeat initiation; each new attempt after failure gets a fresh provider reference. Amount always comes from stored payable snapshot. Payment session lasts 15 minutes, within request lifetime. S35 requires current Signed contract and AwaitingPayment order; S16 requires AwaitingPayment request.

VNPay server notification is authoritative; browser return only opens S35 or S16 with transaction_id and polls status, never marks paid. Verify signature, merchant, provider reference, amount and currency against server data, then commit once using unique provider transaction ID and resource lock. Valid late success may promote Failed/Expired to Succeeded after reconciliation; never downgrade Succeeded. If another attempt already settled the resource, or resource was cancelled/expired, record the received money and initiate a full refund without resurrecting the business object. Never create two paid orders/deliveries from duplicate callbacks. Unknown/mismatched callbacks have no business effect and create a redacted audit event. Reconcile unresolved attempts using provider query after timeout and on operations retry; outage shows Processing, never fabricates success/failure.

Refund requests are idempotent per payment and full-amount only in this version. Company Admin initiates/retries eligible refunds in S37; auto-refunds share the same service. Mark Succeeded only after verified provider response/reconciliation. Failed refund remains visible in S27/S16/S37 and retryable, with admin notification. Do not ask the user for provider secrets in documentation. Before coding the adapter, follow the versioned VNPay protocol contract in integration documentation and sandbox-test signatures, amount conversion, return and notification handling.

## D09 — Merge production

Opt-in is available for a valid saved design/product allowing merge; customer explicitly accepts the versioned merge policy. Promise a fixed 5% subtotal discount and an additional maximum 3 calendar days versus standard production (standard production due 7 days after confirmation; merge production due 10 days). The company honors price/production_due_at even when a batch cannot form. These are production-completion commitments, not guaranteed carrier delivery dates. Record confirmed_at on accepted settlement and production_due_at from the snapshot policy; flag overdue work instead of silently changing the date. Eligibility for admin batch: Confirmed, paid, Signed current contract, opt-in, same company/product/material/color/print method, no existing batch, no cancellation, confirmation within 3 days. Different customer artwork stays distinct per order. Batch requires >=2 orders and total quantity <=10000. Lock/revalidate all orders atomically; one order belongs to at most one batch. Store immutable membership, creator and snapshot. Notify after commit. Batch states Planned -> InProduction -> Completed; Planned -> Dissolved allowed for admin, clearing member batch_ids while retaining history. Dissolution changes no price/signature/payment; normal cancellation becomes possible after unlinking. No changes to membership once InProduction. At the three-day cutoff without a batch, a trusted scheduled job atomically records individual fallback and advances the still-Confirmed order to InProduction while retaining price and production_due_at. It races safely with batching/cancellation under the same row lock. Batch start advances all members atomically; completion does not auto-mark shipped/delivered.

Estimate is explicitly a demo planning model: batch_setup_cost_vnd=100000; gross_setup_saving_vnd=(order_count-1)*100000; customer_discount_vnd=sum(merge_discount_vnd); estimated_net_saving_vnd=gross_setup_saving_vnd-customer_discount_vnd; setup_minutes_saved=(order_count-1)*30. Negative net saving is shown and requires admin acknowledgement, not hidden. Setup time saved is not a shorter customer delivery promise.

## D10 — Analytics and operations

AuditEvent has severity INFO for committed success, WARN for denied/invalid actions, ERROR for dependency/job failures; DEBUG is not a persisted audit severity. Filtering uses this derived stored severity plus action/outcome. Order revenue includes only the single accepted settlement per order; duplicate/late payments and their offsetting refunds belong to a separate reconciliation balance, not sales revenue. Legitimate order cancellation refunds reduce revenue at refunded_at. Export data and totals must use the same classification. Paid/unassigned service cancellation follows the same treatment in the separate service metric.

Analytics is company-scoped and read-only. Default range is last 30 local calendar days, start inclusive/end exclusive, max 366 days; display range/timezone and refreshed_at. Revenue is accepted successful ORDER settlements by paid_at minus refunds of those accepted settlements by refunded_at (exclude duplicate/late receipts and their refunds from sales); show SERVICE revenue separately. Order count uses created_at excluding no states, with cancellation count separate. Customer growth counts distinct customers on their first submitted order in that company during the range; repeat orders never create new customers. Product filter applies to related order/request product. Aggregate only authoritative stored amounts, no sum of pending attempts; zero-data yields zeros, not fabricated examples. CSV/XLSX exports use the same filters, formulas and snapshot watermark, max 100000 rows, prevent spreadsheet formula injection and expose only authorized columns.

System operations: append-only redacted audit events with actor,company,target,action,outcome,request_id,timestamp; no passwords/tokens/full card data. Retain audit events 365 days in the demo policy. Nightly encrypted backup at 02:00 Asia/Ho_Chi_Minh, retain last 7 daily and 4 weekly backups, include database and referenced private assets plus manifest/checksums/schema version. Backup states Queued -> Running -> Succeeded/Failed. Restore requires System Admin reauthentication, explicit backup ID confirmation, checksum/schema check, maintenance mode and successful pre-restore backup; single restore lock; revoke sessions afterward. Payment callbacks are durably queued during maintenance and replayed idempotently with provider reconciliation after restore. Keep payment event/restore audit journal outside the restored snapshot to avoid duplicate fulfillment/refunds. Restore recovery uses the selected snapshot plus a continuous transaction-log archive through the pre-maintenance committed watermark, so orders/payments created after the selected snapshot are reconstructed before callback replay. Require an unbroken verified log chain or reject the restore before activation; arbitrary historical time travel that erases later business transactions is outside this version. Restore failure leaves maintenance enabled with rollback to pre-restore backup available; never report success until validation finishes. Display last verified restore time and failure diagnostics.

Configuration is typed/allowlisted: public company contacts, SMTP connection references, VNPay environment/merchant secret references, design_service_fee_vnd,shipping_vnd,backup schedule/retention. Show merge_discount_percent=5,standard_production_days=7,merge_extra_days=3 as read-only price-policy v1 constants. Defaults are D05/D06/D09/D10. Only System Admin edits global settings; company-specific settings remain same-company scoped. Secret values are write-only references in the UI. Validate a complete version before activation, atomically store/audit, rollback failed validation, notify administrators after commit. No runtime arbitrary script/SQL or unvalidated configuration keys.

## D11 — Screen and navigation baseline

Editable configuration types: design_service_fee_vnd integer 1..9999999999; shipping_vnd integer 0..9999999999 (the final quote must still satisfy payment bounds); daily_backup_time HH:mm in Asia/Ho_Chi_Minh, default 02:00; daily_retention_count 1..30, default 7; weekly_retention_count 1..12, default 4. Retain transaction logs continuously from the oldest retained base through the current committed watermark, and retain referenced asset versions for that interval. Changing retention cannot delete segments/assets needed by retained bases or an active restore. Merchant environment is Sandbox or Production and secrets are opaque secret-store references; contact URLs must be valid HTTPS, phone uses D06's format, email uses D03. No blank/negative fee, unparseable time, arbitrary cron/script or unknown configuration key is accepted.

Support 360px through desktop; stack columns and use labelled horizontal-scroll tables at narrow widths. Keyboard-operable controls, visible focus, logical headings, associated form labels, aria-live status/error announcements, text contrast >=4.5:1 (large text 3:1), and >=24px pointer targets. Preserve user-entered data on recoverable failures. Every view specifies loading, empty, forbidden, error, success and retry behavior. Confirm destructive actions. Disable duplicate submit while pending but also enforce server idempotency.

Keep S01..S40; S14 is product design rules. Add S41 company/staff accounts, S42 merge console, S43 analytics. Contract lists live as a tab in S30, assignment/customer list as tabs in S18/S20, so all retained use cases have a route. Global nav: home S01, catalog S08, designs S17, orders S26, profile S06, notifications S38; staff entry points depend on role. S38 is a reusable panel with full-page fallback. Static about/contact/help/policy content is a named panel on S01, opened without a new business screen ID. External social/contact links render only when valid company contact configuration exists; otherwise omit them. Do not invent real phone numbers/social profiles. Back returns to a validated authorized originating route or safe default (Customer S26, Company Admin S28, Sales Consultant S20, System Admin S41, Guest S01); preserve list filters. Auth redirect retains safe intended route. PNG mockups are historical visual references; these written behaviors override obsolete sample controls/text.

## D12 — Completion and factual inputs

All functions receive concrete schemas, permissions, validation, results and failure behavior through their module spec and D01..D11. Priorities P1 core path/security, P2 staff/management, P3 analytics/operations indicate implementation order, not exclusion. Metadata must not pretend to have named authors, client approval or verified source attachments that are absent. The only pending human-information register is [user-input-needed.md](user-input-needed.md); module documents link it rather than copying questions. Missing original DBIZ2/PDF/session documents are provenance limitations, not blockers for this complete-system specification.
