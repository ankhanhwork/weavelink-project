# WeaveLink implementation decisions

Version 1.2 — 2026-09-23. These are supplementary implementation decisions made under the project owner's approved specification-reconciliation plan. They are not claims about DBIZ2 author intent, a lecturer's approval, or a production legal agreement. Every authoritative decision is also written in the relevant README, module, architecture or screen specification because `ai-files` is not part of the lecturer submission. If a conflict is found, repair both the relevant submitted document and this summary.

## D01 — Actors, tenancy and access

WeaveLink is operated by one made-to-order garment factory, Dony. Dony does not sell ready-made clothing from inventory. A Business Buyer commissions uniforms or garments for internal use. A Reseller Shop supplies its own design, branding or specifications for Dony to manufacture, then sells those manufactured garments to the shop's customers; it does not buy Dony ready-made stock for resale. Product catalogue entries are configurable garment bases and production rules, not finished inventory.

Guest is anonymous; Member means an authenticated active user, not a separately assignable role. Assignable capabilities are Customer, Sales, Sales Admin and System Admin. Public registration creates Customer only. Sales, Sales Admin and System Admin are Dony employees. Buyer-company or shop information is customer and billing data, not a tenant or staff-authorization boundary. Customer access requires ownership; Sales access additionally requires assignment; Sales Admin receives Dony operational authority; System Admin manages Dony staff accounts, configuration, logs and backups but has no implicit customer/order mutation authority. Enforce these rules on the server. Return 401 for missing authentication, 403 for prohibited operations and 404 for inaccessible object identifiers.

Only System Admin provisions internal Dony StaffAccounts. Protect the last active System Admin from deletion, suspension or demotion. Staff deletion is soft deletion plus session revocation and requires operational work to be reassigned or resolved. Business Buyers and Reseller Shops are never created, activated, suspended or deleted through MFG-03.

## D02 — Common data and interfaces

Dony StaffAccount lifecycle is Invited -> Active <-> Suspended -> Deleted. Staff creation atomically creates an inactive employee and a pending invitation. Existing identities authenticate before acceptance; new invited staff set their name/password using S03 invitation mode. Acceptance atomically links or creates the identity, activates the StaffAccount and consumes the invitation. Customer registration and optional BuyerOrganization data never create an internal Dony role.

Identifiers are scoped: MFG-07 and MFG-08 both inherited F-ORD-001 through F-ORD-007. Preserve the source IDs but always reference them as MFG-07/F-ORD-003 or MFG-08/F-ORD-003 outside their own module. FR and US IDs are also module-local. The canonical requirement identity is (module_id, function_id), not function_id alone. UC IDs remain globally unique, including aggregate use cases that map to child functions rather than new duplicate functions.

Use UUID identifiers, ISO-8601 UTC timestamps, display timezone Asia/Ho_Chi_Minh, integer VND amounts and integer quantities. Store immutable created_at and mutable updated_at/version. Money fields never use floating point. User identity, internal role and ownership come from the server session; never trust a submitted customer_id, buyer_organization_id, price, signature IP or role. Optional text is null or trimmed text, not an invented value.

List requests use page >= 1 (default 1), page_size 1..100 (default 20), allowlisted sort/filter fields; responses use items,total,page,page_size. Errors use code,message,field_errors,request_id, with 400 malformed request, 422 invalid fields, 409 stale version/state/duplicate conflict, 429 rate limit and 503 temporary dependency failure. Mutations include expected_version; financially significant create/sign/pay/batch requests additionally use an Idempotency-Key UUID. Same key and same payload returns original result; changed payload is 409. Keep keys at least 7 days and permanent uniqueness for provider transaction/event IDs. Use transactions, unique constraints and an outbox for side effects.

Screen functions return a view model rendered by the client, not a database UI type. Form navigation takes route parameters and current session; forms without business input take no request body. Files are private stored assets referenced by UUID; downloads require access checks and expiring URLs (10 minutes). Upload images: PNG/JPEG/WebP, at most 10 MiB each and 5 files/request; check actual MIME, scan and reject unsafe content. Contract PDFs are generated server-side. Strings render as text; never execute uploaded HTML or template code.

## D03 — Authentication and notifications

Version checks apply to existing objects being edited; a new entity has no client-supplied version unless it references a parent/quote whose version must be checked. Browser mutations require CSRF; signed provider callbacks and trusted scheduled jobs use their own authenticated authority and server-side locks, never a browser session or client expected_version. Registration, invitations and password links are not ordinary authenticated CRUD.

Use email/password, email verification links (24 hours), password-reset links (30 minutes), and staff invitation links (48 hours). Tokens are cryptographically random, stored hashed, single use; resend invalidates prior token. Email is case-normalized, globally unique; full_name 1..100 characters; password 12..128 characters with spaces supported. Store a password hash, never reversible encryption. Generic reset/resend responses do not reveal account existence. Allow at most 5 failed attempts per account/IP in 15 minutes (the fifth returns generic 401; subsequent attempts return 429 until the window clears) and link requests to 3 per account/IP/hour. Password change requires current password and revokes other sessions; reset revokes all sessions. Use revocable server sessions via Secure, HttpOnly, SameSite=Lax cookies, CSRF protection on mutations, 30-minute idle and 24-hour absolute expiry. Post-login return paths must be internal allowlisted routes.

Persist notifications in an outbox in the same transaction as the business event. In-app inbox is authoritative; SMTP email is secondary. Retry email after 1, 5 and 30 minutes, then mark delivery failed for operations retry. Email failure never rolls back signing, payment or assignment. Event/recipient uniqueness prevents duplicate notices. Development uses a local email sink and VNPay sandbox; actual SMTP/provider secrets are environment settings, never committed or requested in the user-input file.

## D04 — Products and designs

Capacity means max_units_per_order (integer 1..10000), not warehouse stock or a reservation pool. The total size quantity must not exceed this limit at quote and submission; return 422 CAPACITY_EXCEEDED otherwise. Capacity changes invalidate unconsumed quotes but never edit submitted orders. Business operators use batching/production queues to schedule accepted work. Product SKU is unique across Dony's catalogue; public canonical URLs use globally unique product UUIDs.

Product states: Draft -> Published -> Hidden; Draft/Hidden/Published -> Archived (terminal). Published requires name, Dony-catalogue-unique SKU, nonnegative unit_price_vnd, category, at least one safe image, supported sizes/colors/materials and manufacturing capacity. Archive removes public visibility but preserves references. No checkout for Hidden/Archived products. Made-to-order capacity is validated at quote/submit, not treated as a reserved stock count. S12 edits product content; S14 edits product design rules for the same product (corrects the duplicate legacy title).

Design is a versioned made-to-order configuration tied to product_id, product_version and customer_id, with optional buyer_organization_id for the represented Business Buyer or Reseller Shop. Use a 2D preview with print-area coordinates; 3D is not required. Saved self-designs and delivered Sales designs are orderable; drafts are not. Validate options against product rules, image bounds and asset access. A changed product/rule invalidates an old quote and requires explicit review; existing submitted orders keep immutable snapshots. Sales delivery creates a new immutable design version and notifies its owner; editing an ordered design creates a copy/version, never changes an order snapshot. Delivered designs and all derived copies/versions retain server-derived source_design_request_id for deferred fee allocation; clients cannot clear or replace it.

## D05 — Design service and consultations

Create DesignRequest as Submitted without displaying/snapshotting a fee or creating payment. Fields: id,customer_id,buyer_organization_id nullable,product_id,requirements (20..5000 chars),attachment_ids,requested_deadline,complexity,rationale/rejection_reason,assessed_by/at,fee_vnd nullable,proposal_version,accepted_fee_version,accepted_fee_vnd,accepted_by/at,fee_order_id nullable,fee_allocation_version,status,assignee,committed_due_at,version. Deadline must be at least 3 calendar days ahead. Submission atomically persists a Sales Admin outbox event and routes S15 to S17 `/designs?tab=requests&request_id={id}`.

Sales Admin uses S18: Submitted -> UnderReview; Simple -> Approved with fee 0; Complex -> FeeProposed with integer 1..9999999999 VND and rationale 1..500 chars; UnderReview -> Rejected with customer-visible reason 1..500 chars. Complex default design_service_fee_vnd is 200000 VND, suggested at assessment and confirmed/overridden by Admin. Customer accepts exact amount/proposal version in S17, recording customer/amount/version/time (accepted_fee_version equals proposal_version) and moving FeeProposed -> Approved. Proposal/approval is immutable; changed work/fee requires eligible cancellation and a new request. Configuration changes never alter existing proposals/accepted fees. Notify owner on assessment outcomes and Admin on acceptance.

Approved -> Assigned -> InProgress -> Delivered; Assigned may deliver directly. Only Sales Admin assigns an active Dony Sales employee through MFG-08; assigned Sales or Sales Admin delivers an immutable design with request provenance. requested_deadline is a preference; committed_due_at is Dony's promise set at assignment. Owner may cancel Submitted/UnderReview/FeeProposed/unassigned Approved without refund, including after acceptance; Assigned/InProgress/Delivered/Rejected reject cancellation. Repeated cancellation returns Cancelled without duplicate effects. All mutations use expected_version and Idempotency-Key; assignment, assessment, acceptance and cancellation lock/revalidate the request, returning 409 for the losing race. Notify owner and Sales Admin after cancellation. Delivered/Cancelled/Rejected are terminal; old request AwaitingPayment/Paid/Expired states and 24-hour expiry are removed.

Requests stand alone until ordered. No order means no invoice, payment, revenue or collection. MFG-06 automatically allocates the accepted fee under D06; MFG-09 renders the same order snapshot. F-DES-007/FR-007 now means assessment, not settlement; F-DES-012/FR-012 is fee acceptance and F-DES-013/FR-013 formalizes existing cancellation. These additions bring MFG-05 to 13 functions and the repository to 96; existing IDs remain stable.

CRM Consultation is separate: New -> Contacted -> InProgress; InProgress -> ClosedWon or ClosedLost; New/Contacted may close early as ClosedLost. Store customer_id, optional buyer_organization_id, sales_user_id, notes and related request/order IDs. Reopening a closed consultation to InProgress requires Sales Admin. Assignment is scoped to a Customer; design request assignment must use that Customer's assigned Sales employee or atomically reassign both. Only assigned Sales and Sales Admin can read notes; Customer sees own request status/delivery, never internal notes. Consultation outcomes do not change order status.

## D06 — Quote, amounts and submission

Merge policy v3 uses an 840,000 VND per-order discount (30% of the 2,800,000 VND setup-cost assumption), capped at merchandise subtotal; standard/merge production targets are 7/10 days after deposit and the eligible pooling window is seven days after confirmed_at (verified deposit). System recommendations never reserve orders or start batches. Only Sales Admin can make the final decision and explicitly start a batch; the scheduler refreshes recommendations and automatically starts individual fallback when an order's seven-day window expires without Admin start. Negative estimated net savings must be shown clearly and do not block or require an acknowledgment. These versioned policies are read-only in ordinary configuration; change only through a reviewed policy version and corresponding specs. The suggested Complex assessment fee and shipping charge remain configurable; accepted fee is frozen on the request and snapshotted into order pricing. Quantity or preference changes create a replacement immutable quote and invalidate the old quote; never mutate quote amounts in place. Submitting one quote twice, even with different idempotency keys, returns the same order via a unique consumed_quote_id constraint. Subtotals and totals use checked integer arithmetic; payment totals must be positive and <=9999999999 VND.

One order contains one product/design version with quantity_by_size (each positive integer, total 1..10000), one optional buyer-organization billing context and one shipping address. Multiple organizations per order and mixed-design orders are outside this version. Address requires recipient_name 1..100, phone 8..15 digits with optional leading +, address_line 1..250, ward 1..100, province 1..100, country VN. Product default unit_price applies equally across sizes; option surcharges are nonnegative VND per unit stored in product rules.

Server quote: subtotal_vnd = sum(size_quantity * (unit_price_vnd + option_surcharge_vnd)); merge_discount_vnd = min(subtotal_vnd, 840000) when opted in under eligible v3 policy, otherwise 0; shipping_vnd = 30000; merge_fee_vnd = 0; tax_vnd = 0; total_vnd = subtotal_vnd - merge_discount_vnd + shipping_vnd + merge_fee_vnd + tax_vnd + design_fee_vnd. Design fee is outside subtotal, never quantity-multiplied or discounted; it is 0 for self-design/Simple/repeat orders and the accepted amount for the allocated first Complex order. Tax zero means classroom demo pricing, not a statement of Vietnamese tax law. No promo codes in this release; omit nonfunctional promo/generate-code controls from the implementation. Display the full breakdown including the separate design fee in S25/S34/S35; old PNG values are illustrative only. A quote lasts 30 minutes and has an immutable quote_id, product/design versions, policy_version, source_design_request_id, accepted_fee_version and fee_allocation_version. Requote expired/changed inputs and require review before submission.

Submitting a valid quote creates an `AwaitingDigitalApproval` Order, items/address/price snapshots and merge preference atomically. Customer cannot submit a different total. No batch is created at checkout. Order contains id,customer_id,buyer_organization_id nullable,design_id,design_version,quote_id,status,merge_opt_in,policy_version,approved_sample_id nullable,contract_id nullable,batch_id nullable,shipping_address,quantity_by_size,price_snapshot (including design_fee_vnd),source_design_request_id,accepted_fee_version,version,created_at. Buyer organization is snapshotted billing/customer context, not a tenant authority. Monetary/configuration changes apply only to new quotes and never override an accepted request fee.

The accepted fee attaches to the first successfully created order from the delivered request design or any derived version retaining source_design_request_id. First means the allocation transaction that commits under the request lock, not the first quote. Quote stores accepted_fee_version (null for self-design/Simple) and fee_allocation_version (null when no Complex allocation applies); order creation revalidates both and atomically writes fee_order_id, increments allocation version and snapshots the fee. Concurrent contenders receive 409 DESIGN_FEE_ALLOCATION_CONFLICT and must requote/review; never silently change a reviewed total.

While the fee-bearing order has not reached InProduction, further orders from that Complex request lineage are blocked with 409 DESIGN_FEE_ORDER_PENDING, including while cancellation/payment/refund resolution is pending. Once it reaches InProduction, record the retained allocation; subsequent orders carry design_fee_vnd 0. If cancelled earlier, retain its immutable fee line and release the allocation only after all payment attempts are authoritatively resolved and any required policy-based refund succeeds. A subsequent late receipt is refunded against the cancelled order and never changes the released allocation. The next newly created order after release carries the fee; never retrofit another order. Simple requests and self-designs have fee 0 and no allocation restriction. No order means no invoice, transaction, revenue or collection. Admin cannot override/add another fee. All final amounts must be positive and <=9999999999 VND.

## D07 — Order and contract lifecycle

Canonical progression: `AwaitingDigitalApproval -> DigitalDesignApproved -> SampleInPreparation -> SampleShipped -> PendingContract -> AwaitingDeposit -> Confirmed -> InProduction -> Shipped -> DeliveredAwaitingBalance -> Completed`. Customer approval binds the digital-design/quote version. Dony then prepares and dispatches a versioned physical sample. Customer approval of the received current sample opens `PendingContract`; revision preserves evidence and returns through a new immutable design/quote approval cycle. Signing changes `PendingContract -> AwaitingDeposit`; verified DEPOSIT changes `AwaitingDeposit -> Confirmed`; Customer receipt or authorized delivery proof changes `Shipped -> DeliveredAwaitingBalance`; verified BALANCE alone changes it to `Completed`. Eligible pre-deposit states and pre-production unbatched Confirmed may be cancelled. A cancelled order stays Cancelled while any policy-based refund is tracked separately. Assigned Sales or Sales Admin performs staff-owned sample/fulfillment actions; neither can impersonate Customer approvals or bypass payment gates. Skipped/reversed transitions are 409.

Sales Admin generates a contract only for a `PendingContract` order with a current Approved physical sample. The versioned contract binds approved design/sample IDs, order snapshots, contract_total_vnd, separate design_fee_vnd, deposit_percent, `deposit_due_vnd = floor(contract_total_vnd × deposit_percent / 100)`, remaining-balance formula and payment-policy version; no manual amount override. Contract states Draft -> Ready -> Signed; Draft/Ready -> Superseded; Draft/Ready/Signed -> Voided on eligible cancellation. Publish Ready only after PDF storage succeeds. Signing uses authenticated Customer, consent, matching typed name, recent password and a one-time challenge bound to contract/version/hash. Transaction locks contract/order and rejects stale sample or document versions; only successful signing changes order to `AwaitingDeposit`. This is an application acknowledgement with audit trail, not a certified digital signature.

## D08 — Payment and refund

PaymentTransaction belongs to purpose `DEPOSIT` or `BALANCE` and exactly one order_id; generic ORDER and SERVICE purposes are inactive. Fields include id,purpose,order_id,customer_id,buyer_organization_id nullable,amount_vnd,currency=VND,status,provider references,timestamps,refund status and version. One active Pending attempt exists per order/purpose. DEPOSIT is payable only for a Signed contract in `AwaitingDeposit` and uses the stored deposit_due_vnd. BALANCE is payable only after receipt in `DeliveredAwaitingBalance` and uses `contract_total_vnd - accepted_deposit_vnd - accepted_order_credit_vnd`. Payment session lasts 15 minutes. S16 is retired, has no screen or redirect, and a legacy URL returns non-mutating 410 Gone.

VNPay server notification is authoritative; browser return only opens S35 and polls status. Verify signature, merchant, provider reference, purpose, amount and currency, then commit once using unique provider transaction ID and order-purpose lock. Accepted DEPOSIT confirms the order; accepted BALANCE completes it. A late success after cancellation records captured money and starts the policy-authorized refund without resurrecting the order. Unknown/mismatched callbacks have no business effect and create a redacted audit event. Provider outage shows Processing, never fabricated success/failure.

Refund requests are idempotent per payment and full-amount only in this version, including the design-fee component; allocation release follows D06. Sales Admin initiates/retries eligible refunds in S37; auto-refunds share the same service. Mark Succeeded only after verified provider response/reconciliation. Failed refund remains visible in S27/S37 and retryable, with admin notification. Do not ask the user for provider secrets in documentation. Before coding the adapter, follow the versioned VNPay protocol contract in integration documentation and sandbox-test signatures, amount conversion, return and notification handling.

## D09 — Merge production

Customer explicitly accepts versioned merge policy on eligible products/variants. Dony offers 840000 VND per opted-in order (30% of the 2800000 VND setup-cost planning assumption), capped at subtotal; standard and merge production targets are deposit_at+7 and +10 calendar days. `window_end_at=confirmed_at+7 days`; no weekday or fixed-clock cutoff. A scheduler checks at least every five minutes and recommends compatible groups; eligibility requires verified deposit/Confirmed, opted in, same Dony facility and product/material/color/print method key, unbatched and uncancelled. Different customer artwork remains distinct per order. Batch requires >=2 members and aggregate quantity <=10000. Only Sales Admin can explicitly start a selected group after final review; lock/revalidate atomically. Recommendations do not reserve orders. Store immutable membership, approver, start time and estimate snapshots. At window expiry without an Admin-started batch, scheduler records fallback and automatically starts individual production through MFG-07. Overdue scheduler failures trigger retry and alert. Estimate gross=(n−1)*2800000 VND; discount=sum member discounts; net=gross-discount; setup minutes saved=(n−1)*120. Show negative net transparently; do not block or require a separate acknowledgment. Programme net subtracts all discounts on merge orders reaching production, including fallback. A batch due date is the earliest member due; completion does not auto-mark individual orders shipped/delivered.

Programme break-even share of batched opted-in orders is `30%*k/(k−1)` at batch size k: 60% for pairs and 45% for triples. Setup-time savings are not a shorter customer production promise.

## D10 — Analytics and operations

AuditEvent has severity INFO for committed success, WARN for denied/invalid actions, ERROR for dependency/job failures; DEBUG is not a persisted audit severity. Filtering uses this derived stored severity plus action/outcome. Recognized revenue is the immutable contract total once an order reaches Completed, net recognized refunds; cash collected is reported separately from accepted DEPOSIT/BALANCE settlements, net refunds. Duplicate/late receipts and their offsetting refunds are excluded together from sales revenue and cash metrics. Legitimate order cancellation refunds reduce recognized revenue at refunded_at. Export data and totals use the same classification. Design-request cancellation has no payment or refund; eligible order refunds include the design-fee component.

Analytics is Dony-wide and read-only for Sales Admin. Revenue is recognized once from the immutable contract total when an order becomes Completed, net recognized refunds. Cash collected separately sums accepted DEPOSIT/BALANCE settlements by paid_at net refunds; deposits are not revenue and installments are never double-counted. Design-fee revenue is an included completed-order component. Default range is last 30 local calendar days, start inclusive/end exclusive, max 366 days; show range/timezone/refreshed_at. Order count uses created_at with cancellation count separate. Aggregate only authoritative stored amounts; zero-data yields zeros. Exports use identical filters/formulas/watermark, cap 100000 rows and prevent formula injection.

System operations: append-only redacted audit events with actor,company,target,action,outcome,request_id,timestamp; no passwords/tokens/full card data. Retain audit events 365 days in the demo policy. Nightly encrypted backup at 02:00 Asia/Ho_Chi_Minh, retain last 7 daily and 4 weekly backups, include database and referenced private assets plus manifest/checksums/schema version. Backup states Queued -> Running -> Succeeded/Failed. Restore requires System Admin reauthentication, explicit backup ID confirmation, checksum/schema check, maintenance mode and successful pre-restore backup; single restore lock; revoke sessions afterward. Payment callbacks are durably queued during maintenance and replayed idempotently with provider reconciliation after restore. Keep payment event/restore audit journal outside the restored snapshot to avoid duplicate fulfillment/refunds. Restore recovery uses the selected snapshot plus a continuous transaction-log archive through the pre-maintenance committed watermark, so orders/payments created after the selected snapshot are reconstructed before callback replay. Require an unbroken verified log chain or reject the restore before activation; arbitrary historical time travel that erases later business transactions is outside this version. Restore failure leaves maintenance enabled with rollback to pre-restore backup available; never report success until validation finishes. Display last verified restore time and failure diagnostics.

Configuration is typed/allowlisted: public Dony contacts, SMTP connection references, VNPay environment/merchant secret references, design_service_fee_vnd (suggested Complex assessment fee; future assessments only), shipping_vnd and backup schedule/retention. Show the MFG-10 policy version's per-order discount amount (840,000 VND, capped at merchandise subtotal), seven-day pooling window, Sales Admin final batch approval/start rule, standard production target (7 days after deposit) and merged target (10 days after deposit) as read-only merge-policy values. Defaults are D05/D06/D09/D10. Only System Admin edits global Dony settings. Secret values are write-only references in the UI. Validate a complete version before activation, atomically store/audit, roll back failed validation and notify administrators after commit. No runtime arbitrary script/SQL or unvalidated configuration keys.

## D11 — Screen and navigation baseline

Editable configuration types: design_service_fee_vnd integer 1..9999999999, default 200000 for Complex assessment; Simple uses 0; shipping_vnd integer 0..9999999999 (the final quote must still satisfy payment bounds); daily_backup_time HH:mm in Asia/Ho_Chi_Minh, default 02:00; daily_retention_count 1..30, default 7; weekly_retention_count 1..12, default 4. Retain transaction logs continuously from the oldest retained base through the current committed watermark, and retain referenced asset versions for that interval. Changing retention cannot delete segments/assets needed by retained bases or an active restore. Merchant environment is Sandbox or Production and secrets are opaque secret-store references; contact URLs must be valid HTTPS, phone uses D06's format, email uses D03. No blank/negative fee, unparseable time, arbitrary cron/script or unknown configuration key is accepted.

Support 360px through desktop; stack columns and use labelled horizontal-scroll tables at narrow widths. Keyboard-operable controls, visible focus, logical headings, associated form labels, aria-live status/error announcements, text contrast >=4.5:1 (large text 3:1), and >=24px pointer targets. Preserve user-entered data on recoverable failures. Every view specifies loading, empty, forbidden, error, success and retry behavior. Confirm destructive actions. Disable duplicate submit while pending but also enforce server idempotency.

The active screen catalogue contains 45 entries: S01-S15 and S17-S46. S16 is retired and has no screen, PNG, redirect, or payment workflow; a legacy URL returns non-mutating 410 Gone. S14 is product design rules. S41 staff accounts, S42 merge console, and S43 analytics complete the catalogue. Contract lists live as a tab in S30, assignment/customer list as tabs in S18/S20, so all retained use cases have a route. Global nav: home S01, catalog S08, designs S17, orders S26, profile S06, notifications S38; staff entry points depend on role. In MVP hide Profile/S06. After staff login, MVP Sales Admin lands on S28; pre-provisioned Sales and System Admin accounts are authentication/authorization test identities only and land on S01 without staff-only MVP actions. S20/S41 and other deferred or unauthorized staff routes return 404/403 under the route-disclosure rule. Static about/contact/help/policy content is a named panel on S01, opened without a new business screen ID. External social/contact links render only when valid Dony contact configuration exists; otherwise omit them. Do not invent real phone numbers/social profiles. Full-system default Back destinations remain Customer S26, Sales Admin S28, Sales S20 and System Admin S41; in MVP use S01 for Sales/System Admin because S20/S41 are excluded. Preserve list filters. Auth redirect retains safe intended route. PNG mockups are visual references; written screen behaviors override obsolete sample controls/text.
